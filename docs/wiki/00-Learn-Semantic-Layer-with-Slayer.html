用 SLayer 学语义层 · 完整学习手册

本手册面向初学者，结合开源项目 SLayer ，从「语义层是什么」讲到「一次查询是如何从 MCP 一路走到数据库并把结果带回来」。 所有内容均配有 Mermaid 图示与可运行的代码片段。

建议阅读路径：第 1 章（是什么）→ 第 2 章（数据链条总览）→ 第 3、4 章（核心模型与查询生命周期）→ 第 5、6 章（SQL 与存储）→ 第 7 章以后按需查阅。文中所有 src/... 形式的路径都对应 SLayer 仓库内的实际文件。
阅读约定：术语在首次出现时会在第 13 章术语表中给出定义；代码示例省略了与讲解无关的 import 与类型注解。

1.1 什么是语义层（Semantic Layer）

在传统数仓体系里，业务方想要"最近 7 天华东大区 GMV"，需要让分析师写一条复杂的 SQL 联表查询。 每换一个业务问题就要改 SQL，且不同人写出的指标口径常常对不上。

语义层做的就是一件事：把"业务口径"沉淀为可复用、可治理、可下推的中间层。 它向上提供面向业务的"指标 / 维度 / 筛选"语义，向下翻译成具体数据库的 SQL。

flowchart LR subgraph BIZ[业务方] B1[分析师] B2[BI 工具] B3[AI Agent] end subgraph SL[语义层 SLayer] S1[指标 / 维度 / 筛选] S2[缓存 / 权限 / 行级安全] S3[方言适配] end DB[(数据仓库
Snowflake / DuckDB / Postgres ...)] BIZ -->|业务问题| SL SL -->|标准 SQL| DB DB -->|结果| SL SL -->|统一口径| BIZ

来源：github.com/MotleyAI/slayer

1.2 SLayer 是什么

SLayer 是一个面向 AI Agent 时代的语义层，核心定位：

  • 轻量、嵌入式：单进程、几百 MB 内存即可运行
  • 多语言适配：Python API + Flight SQL + Postgres 协议 + REST + MCP
  • 多方言：内置 DuckDB / Snowflake / BigQuery / Postgres / ClickHouse
  • 多存储：YAML（Git 友好）+ SQLite（嵌入式）+ 内存
  • 原生 RLS / SESSION POLICY：行级安全与会话策略
  • AI 记忆：把"业务知识 / 历史问答"存入语义层本身，供 Agent 检索

1.3 SLayer 的 6 层架构

flowchart TB L1[Surface 表面层
CLI / REST / MCP / Flight SQL / Postgres Wire] L2[Service 服务层
query / schema / models / memories / search] L3[Engine 引擎层
SlayerQueryEngine + 缓存 + 计划] L4[Core 核心模型
SlayerModel / SlayerQuery / Join / RLS] L5[SQL 层
SQLGenerator + 方言策略] L6[Storage 存储层
YAML / SQLite / Memory] L1 --> L2 --> L3 --> L4 --> L5 --> L6

每一层只依赖下层，对外只暴露上层的能力。这就是为什么 SLayer 可以用同一条流水线同时支撑 BI 工具、REST 调用与 AI Agent。

2.2 每一跳到底做了什么

第 1 跳：MCP 接收工具参数

FastMCP 把 query 工具的参数（source_model、measures、dimensions、filters…）打包成 dict。 MCP 层只做"协议适配"，不做任何业务校验。

第 2 跳：构造 SlayerQuery

用 Pydantic 把 dict 强类型化为 SlayerQuery。这一步把"业务侧的模糊描述"冻结成"结构化算子"。

第 3 跳：归一化输入

_normalize_input 处理 3 类输入： dict（直接使用）、SlayerQuery（已是合法对象）、str（按 source_model 名查表）。

第 4 跳：拓扑排序

当一次调用涉及多个 model（如跨模型 join 或 named query）时，用 Kahn 算法排拓扑序，保证依赖在前。

第 5-6 跳：取模型 + enrich

从 StorageBackend 拿到 SlayerModel，再交给 enrich_query： 解析 measure、dimension、time_dim 引用，处理 transform、cross-model 引用、filter AST。

第 7 跳：生成 SQL

SQLGenerator 把 EnrichedQuery 翻译成目标方言的 SQL；具体拼装交给 Dialect.build_xxx()。

第 8 跳：应用 Session Policy（RLS）

用 ast 解析 SQL，找出每张物理表 FROM t，把 t 重写为 (SELECT * FROM t WHERE <policy>) t。 这一步是行级安全的关键。

第 9 跳：执行 SQL

SlayerSQLClient 通过 SQLAlchemy 异步引擎把 SQL 发到目标数据库。

第 10 跳：包装响应

把 rows、sql、attributes、runtime_ms 打包成 SlayerResponse。

第 11 跳：格式化输出

MCP 决定以 markdown / json / csv 返回给 Agent。Agent 拿到的是可读且带 SQL 证据的结果。

3.1 核心数据模型：SlayerModel 与 Column

SlayerModel 是"业务实体"的声明；每张表对应一个 Model。

@dataclass
class SlayerModel:
    name: str                           # 逻辑表名
    table: str | Table                # 物理表 / Table 对象
    columns: list[Column]              # 维度 + 度量
    measures: list[ModelMeasure]        # 度量
    joins: list[ModelJoin]            # 与其他 Model 的连接
    primary_key: str | list[str]      # 主键
    defaults: ModelDefaults | None       # 默认度量/维度
    access_grants: list[str]            # RBAC: 谁能查
    session_policies: list[SessionPolicy]  # RLS: 行级过滤

Column 是"字段"——既可以是 dimension，也可以是 measure。 它把数据库列名 + 业务语义 + 表达"列怎么算"的表达式绑在一起。

@dataclass
class Column:
    name: str              # 业务名
    type: ColumnType      # dimension | measure | time
    expr: str | None     # SQL 表达式或列名
    agg: str | None      # sum/count/avg/min/max
    sql: str | None      # 复杂表达式
    description: str | None  # 描述（供 AI 检索）

3.2 SlayerQuery：一次查询的"算子集合"

用户每次调用语义层都对应一个 SlayerQuery。它由若干算子组合而成：

flowchart LR Q[SlayerQuery] Q --> M[measures
要看哪些指标] Q --> D[dimensions
按什么分组] Q --> F[filters
要过滤什么] Q --> O[order_by
排序] Q --> L[limit / offset
分页] Q --> T[time_dim
时间维度封装] Q --> C[cross_model_dims
跨模型维度] 
@dataclass
class SlayerQuery:
    source_model: str                # 主模型
    measures: list[str] = []        # 指标名
    dimensions: list[str] = []      # 维度名
    filters: list[Filter] = []      # 过滤条件
    order_by: list[OrderBy] = []    # 排序
    limit: int | None = None          # LIMIT n
    offset: int | None = None         # OFFSET n
    time_dim: TimeDim | None = None   # 时间维度封装
    cross_model_dims: list = []     # 跨模型维度

为什么叫"算子"？因为它和 SQL 是一一映射的： measures → SELECT SUM(...)、filters → WHERE、order_by → ORDER BY、… 业务方写"算子"，引擎翻译成 SQL。

3.3 ModelJoin 与 RLS / SessionPolicy

ModelJoin 描述"两个 Model 之间怎么连"：

@dataclass
class ModelJoin:
    model: str           # 目标 Model
    type: JoinType       # left / inner / full
    on: str             # 连接条件 SQL 表达式
    relationship: str      # one_to_one / many_to_one / …

SessionPolicy 描述"行级安全策略"：

@dataclass
class SessionPolicy:
    name: str                 # 策略名
    when: str = "true"        # 何时生效的 SQL 谓词
    where: str = "true"       # 注入到 WHERE 的谓词
    bind: dict[str, Any] = {} # 占位符绑定
一个华东大区销售总监登录后，bind={"tenant_id": "east_china"}； 策略把每张物理表 FROM orders 改写为 FROM (SELECT * FROM orders WHERE tenant_id = :tenant_id) orders。 应用代码完全无感。

4.1 查询生命周期的 7 步流水线

从 engine.execute(query) 入口到返回 SlayerResponse，内部走的是一条 7 步流水线：

flowchart TB S1[1. 归一化输入] --> S2[2. 拓扑排序] S2 --> S3[3. 拉取模型] S3 --> S4[4. enrich_query] S4 --> S5[5. 生成 SQL] S5 --> S6[6. 应用 Session Policy / RLS] S6 --> S7[7. 执行 + 缓存 + 包装响应]
Step 1归一化输入（_normalize_input）
兼容 3 种输入形态：dict、SlayerQuery、str（按 source_model 查表）。 把外部世界千奇百怪的"提问方式"折算成内部统一对象。
Step 2拓扑排序（_topologically_order_queries）
多 stage 时（如多 named query 嵌套、或跨模型 join），用 Kahn 算法做拓扑排序，保证依赖在前。
Step 3拉取模型（storage.get_model）
从 YAMLStorage / SQLiteStorage 拿 SlayerModel 完整定义。 这一步是"读模型"，没有任何业务计算。
Step 4enrich_query
把 measure / dimension 名解析回 Column，处理 transform、cross-model 引用、filter AST、time grain 折叠。 输出 EnrichedQuery，是"业务的最终算子"和"模型的最终元数据"合并的产物。
Step 5生成 SQL（SQLGenerator.generate）
SQLGenerator 把 EnrichedQuery 翻译成目标方言的 SQL。底层用 SQLGlot 这种"AST 化"的 SQL 工具，确保语法可校验、方言可切换。
Step 6应用 Session Policy（apply_session_policy）
遍历 SQL 中每张物理表，把 FROM t 改写成 FROM (SELECT * FROM t WHERE <policy>) t。 RLS 注入与 SQL 重写在同一阶段完成。
Step 7执行 + 缓存 + 包装
SlayerSQLClient 通过 SQLAlchemy 异步执行 SQL，结果连同 SQL、attributes、runtime_ms 一起包装为 SlayerResponse。 命中缓存的查询直接返回，绕过 Step 4-6。

5.1 SQL 生成：从 EnrichedQuery 到方言 SQL

SLayer 的 SQL 生成采用"AST 化 + 方言策略"两层设计：

flowchart LR EQ[EnrichedQuery] --> GEN[SQLGenerator] GEN --> AST[SQLGlot AST] AST -->|DuckDB dialect| D1[DuckDB SQL] AST -->|Postgres dialect| D2[Postgres SQL] AST -->|Snowflake dialect| D3[Snowflake SQL] AST -->|BigQuery dialect| D4[BigQuery SQL] AST -->|ClickHouse dialect| D5[ClickHouse SQL]

为什么用 AST 而不是字符串拼接？

  • 类型安全：每个节点都能校验类型、列是否存在
  • 方言切换：换方言只是换"输出器"，AST 不动
  • 易测试：可以直接断言 AST 结构，不依赖字符串
  • 可优化：将来加 hint、改 join 顺序、注入 predicate 都很自然

5.2 方言适配：每种数据库都有自己的"方言策略"

每种方言实现 Dialect 接口的几个 build_xxx() 方法：

class Dialect:
    def build_select(self, eq): ...
    def build_where(self, filters): ...
    def build_group_by(self, dims): ...
    def build_order_by(self, orders): ...
    def build_limit(self, limit, offset): ...
    def quote_identifier(self, ident): ...

差异点举例：

差异DuckDBSnowflakeBigQuery
取 TOP NSELECT ... LIMIT nSELECT ... LIMIT nSELECT ... LIMIT n
数组列展开UNNEST(arr)FLATTEN(input => arr)UNNEST(arr)
时分桶DATE_TRUNC('day', ts)DATE_TRUNC('DAY', ts)TIMESTAMP_TRUNC(ts, DAY)

7. 引擎内部（Engine Internals）

本节带你看清 SlayerQueryEngine 的"发动机舱"。完整文档见 术语表， 深入讲解见 07-Engine-Internals.md。

flowchart LR Q[SlayerQueryEngine] --> C[Query Cache] Q --> P[Query Planner] Q --> I[Auto Ingestor] Q --> D[Schema Drift Detector] Q --> M[Memory Adapter]
  • Query Cache：基于 SQL 文本 + bind 参数的 LRU/TTL 缓存，命中直接返回，绕过 enrich → 生成 → 执行。
  • Query Planner：多 stage 时做 Kahn 拓扑排序，决定哪个 query 先算。
  • Auto Ingestor：当源表没有匹配 Model 时，可一键反向生成 YAML Model。
  • Schema Drift Detector：定期检查物理表 schema 与 Model 声明是否一致，发现漂移即报警。
  • Memory Adapter：让"AI 记忆"也能通过语义层查询、检索、写入。

8. BI 接入层（Flight SQL / Postgres Wire）

BI 工具（Superset / Metabase / Power BI）通常只能通过"标准协议"连接。SLayer 通过两个 Facade 把内部查询翻译成标准协议消息：

flowchart LR BI[BI 工具] -->|Arrow Flight SQL| F1[flight_sql facade] BI -->|Postgres Wire| F2[pgwire facade] F1 --> T[shared translator] F2 --> T T --> E[SlayerQueryEngine]

共享的 translator 负责：

  • 识别 SELECT ... FROM model_name 模式
  • 把 SQL 中的列/聚合映射回 SlayerQuery
  • 走和 MCP 完全相同的 7 步流水线
  • 结果再翻译成 Arrow 记录或 Postgres 行

10. AI 记忆与搜索

SLayer 把"业务知识 / 历史问答"也存入语义层，让 Agent 能跨会话检索。

flowchart LR M[Memory] --> IDX1[BM25 索引] M --> IDX2[Tantivy 全文索引] M --> IDX3[Embedding 向量索引] Q[查询] --> S[SearchService] IDX1 --> S IDX2 --> S IDX3 --> S S --> RRF[RRF 融合排序] --> RES[Top-K 记忆]

三种通道并行召回，再用 RRF（Reciprocal Rank Fusion）融合，兼顾精确匹配、词项匹配、语义匹配。

11. 导入器（dbt Semantic Layer / OSI）

如果你已经在用 dbt Semantic Layer 或 OSI（Open Semantic Interchange），可以直接导入：

# 从 dbt Semantic Layer YAML 导入
slayer import dbt ./dbt/models/semantic/ -o ./models/

# 从 OSI YAML 导入
slayer import osi ./osi/datasets.yml -o ./models/

导入器会把对方的语义模型一对一翻译成 SLayer 的 SlayerModel 描述。详细转换规则见 11-Importers.md。
