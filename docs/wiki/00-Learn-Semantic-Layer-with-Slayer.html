SLayer 语义层学习手册

这份教程面向初学语义层（Semantic Layer）的开发者，以开源项目 SLayer 为案例，从最朴素的"什么是语义层"出发，逐步拆解整个项目代码结构， 重点讲清楚一条查询是如何从 MCP 客户端一路走到数据库的。

Pydantic v2 sqlglot AST SQLAlchemy 2.0 MCP stdio / SSE 8+ 数据库方言 async-first

1. 什么是语义层？

语义层（Semantic Layer）是位于原始数据库与使用者（BI 工具、Agent、应用） 之间的一层"领域模型翻译器"。它的核心任务是：

把"业务意图"翻译成"数据库 SQL"

  • 业务侧只关心"我想看销售额、按地区分组、上个月的数据"——这是意图。
  • 数据库侧只懂"SELECT … FROM … WHERE … GROUP BY …"——这是实现。
  • 语义层在中间架一座桥：定义统一的度量（Measure）和维度（Dimension）， 把意图映射到不同方言的 SQL。

语义层通常要做这些事：

1. 元数据管理
定义"什么表、什么列、什么指标"是业务可见的。
2. 查询转译
把"我要 revenue:sum"翻译成具体方言的 SUM()。
3. 连接解析
自动决定多表之间怎么 JOIN、按什么键。
4. 访问控制
透明地注入"行级安全（RLS）"的 WHERE 谓词。
5. 多接口暴露
同一份模型通过 REST/MCP/BI 网关等服务出去。

为什么选 SLayer？

SLayer 是 MotleyAI 开源的轻量、Agent 优先的语义层。 跟 Cube / dbt Semantic Layer 不同的是：

特性SLayer传统语义层
运行时编辑模型支持（无 build）需要 build / refresh
查询时聚合同一个列可 :sum / :avg / :count度量需预定义
跨数据库同一模型跨 PG/MySQL/ClickHouse/…通常绑死一种
接口MCP / REST / Flight SQL / pg-wire通常只有 SQL / REST
依赖单 Python 进程常需独立服务

一个查询的例子

想了解"上个月各状态订单数"——你只需要给 SLayer 这样的结构化描述：

# 自然语言版：上个月各状态订单数 { "source_model": "orders", "measures": [{"formula": "*:count"}], "dimensions": ["status"], "time_dimensions": [{ "dimension": "ordered_at", "granularity": "month", "date_range": ["2026-06-01", "2026-06-30"] }] }

SLayer 会自动产出针对目标数据库方言的 SQL：

SELECT DATE_TRUNC('month', orders.ordered_at) AS orders.ordered_at_month, orders.status AS orders.status, COUNT(*) AS orders._count FROM main.orders AS orders WHERE orders.ordered_at BETWEEN '2026-06-01' AND '2026-06-30' GROUP BY 1, 2 ORDER BY 1

你不需要写任何 SQL、不需要关心底层是 Postgres 还是 SQLite——这就是语义层的承诺。

8 步精简版

  1. MCP 接收：FastMCP 收到 query(...) 工具调用，把参数打包成 dict。
  2. 类型校验：SlayerQuery.model_validate(data) 校验输入并自动 Pydantic 化。
  3. 引擎入口：await engine.execute(query, ...) 触发核心流水线。
  4. 归一化 & 排序：把 dict / list / str 统一成 SlayerQuery；多 stage 时 Kahn 拓扑排序。
  5. 模型解析：从 StorageBackend 取 SlayerModel，把跨模型引用连成 JOIN 图。
  6. 富化 (Enrich)：把"revenue:sum"这种字符串解析成完整 SQL 表达式树；处理 transform、跨模型度量、distinct dedup。
  7. 生成 SQL：SQLGenerator 用 sqlglot AST 构建最终 SQL，委托给具体方言。
  8. 执行：SlayerSQLClient 通过 SQLAlchemy 异步驱动执行 SQL 并返回行。

SlayerModel 详解

SlayerModel 是语义层的核心——它定义一张"业务可用的虚拟表"。它有三种 source 模式，三选一：

三种 source 模式互斥

  • sql_table：直接绑物理表 public.orders
  • sql：自定义 SQL 子查询 SELECT … FROM …
  • source_queries：多阶段查询链（DAG），每段是一个 SlayerQuery
class SlayerModel(BaseModel): version: int = 7 # 当前 schema 版本 name: str # ^[a-zA-Z_][a-zA-Z0-9_]*$，不含 . : __ description: str | None = None data_source: str | None = None # 物理表底模型必填 sql_table: str | None = None # 模式 1：物理表 sql: str | None = None # 模式 2：SQL 子查询 source_queries: list[SlayerQuery] | None = None # 模式 3：查询链 columns: list[Column] = [] # 统一列（v2 起 dim+measure 合并） measures: list[ModelMeasure] = [] # 命名公式库 aggregations: list[Aggregation] = [] # 自定义聚合 joins: list[ModelJoin] = [] # LEFT/INNER 声明 filters: list[str] = [] # 总是应用的 WHERE（Mode A SQL） default_time_dimension: str | None = None query_variables: dict[str, Any] = {} # 给 {var} 占位符的默认值 meta: dict[str, Any] = {} # 用户自定义元数据

SlayerQuery 详解

SlayerQuery 是用户每次查询的"描述"。它和 SlayerModel 是 1:N 关系：

class SlayerQuery(BaseModel): version: int = 3 name: str | None = None # 链式 stage 名（首段之外都需要） source_model: str | SlayerModel | ModelExtension measures: list[MeasureSpec] = [] # {"formula": "revenue:sum"} 形式 dimensions: list[str | ColumnRef] = [] time_dimensions: list[TimeDimension] = [] # 带 granularity / date_range filters: list[str] = [] # Mode B DSL，含 {var} 占位符 order: list[OrderBy] = [] limit: int | None = None offset: int | None = None variables: dict[str, Any] = {} # 给 {var} 提供值 distinct_dimension_values: bool = True # Cube.js 风格 dim 自动去重 model_config = ConfigDict(extra="forbid") # 严格：拒绝未知字段
多 stage DAG：当 source_queries 或传入的 query=[] 是列表时，整个查询是一个 DAG。 引擎用 Kahn 算法自动拓扑排序，最后一段始终是 entry point（它的结果就是返回值）。

Mode A / Mode B 引用

SLayer 把"如何解析字符串引用"分成两套规则，混用得当才不会出 bug：

模式适用字段解析器允许写法
Mode A (SQL) Column.sql、Column.filter、SlayerModel.filters sqlglot 解析 任意 SQL 表达式，__ 分隔 join path
Mode B (DSL) ModelMeasure.formula、SlayerQuery.measures / filters Python AST 解析 revenue:sum、customers.regions.name、transform 调用
# Mode A (SQL) — 解析器是 sqlglot columns: - name: full_name sql: "first_name || ' ' || last_name" # 任意 SQL - name: customer_region sql: "customers__regions.name" # __ 跨模型 # Mode B (DSL) — 解析器是 Python AST measures: - name: aov formula: "revenue:sum / *:count" # 聚合后缀 - name: order_count formula: "orders.id:count_distinct" # 显式聚合 - name: mom_growth formula: "change_pct(revenue:sum)" # transform

两者的"白名单"必须共享：core/formula.py 中的 SCALAR_PASSTHROUGH 列出了所有可用的标量函数（coalesce、abs、round、greatest、lower、…）。

第 1 步：输入归一化（_normalize_input）

引擎接受 4 种输入形态，统一转成 SlayerQuery：

多 stage 时调 _topologically_order_queries： 自实现 Kahn 算法，从 source_model / joins[].target_model 抽取依赖， 校验缺失名 / 重名 / 自指 / 环。最后一段固定为根（entry point）。

第 2 步：富化（enrich_query）

enrich_query 是"查询编译"的核心。 它接收 SlayerQuery + 已解析的 models，产出 EnrichedQuery。

富化后的对象里，所有 SQL 表达式都是裸的 sqlglot exp.Expression 节点——模型查找工作全部完成，下游无需再访问 storage。

几个富化期的关键转换

  • 字符串 "revenue:sum" → MeasureSpec(formula="revenue:sum", aggregation="sum", source_column=Column(...))
  • 跨模型 "customers.score:avg" → CrossModelMeasure（走 inner CTE + LEFT JOIN）
  • change / change_pct → 反糖成 hidden time_shift + 算术，便于统一处理
  • 计算型过滤器（如 change(revenue:sum) > 0）→ 抽出为 hidden field，在外层 WHERE 应用

第 3 步：SQL 生成（SQLGenerator.generate）

SQLGenerator 的设计原则：

1. 只接受 EnrichedQuery
不再访问 storage，所有查找已在富化期完成。
2. AST 化构造
用 sqlglot 的 exp.* 节点而非字符串拼接。
3. 委托方言
所有"此方言特有"的逻辑都在 SqlDialect 子类上。
4. CAST + 保留字统一处理
在最终 emit 之前统一套 CAST 和加引号。

第 4 步：行级安全（apply_session_policy）

如果构造 engine 时传了 SessionPolicy，SQL 生成后会做一次重写：

flowchart LR A[final_sql] --> B[sqlglot parse AST] B --> C[遍历所有 From 子句] C --> D{是物理表?} D -->|是| E[FROM t →
FROM SELECT * FROM t WHERE col=val AS t] D -->|否 - CTE/derived| F[跳过] E --> G[Join rule 走 EXISTS 半连接] G --> H[SQL 注入安全 exp.convert] F --> I H --> I[新 sql]
安全性细节：所有值通过 exp.convert 注入，不是字符串拼接——所以无法 SQL 注入。 强制 backstop：任何含 JoinFilterRule 的策略必须同时含至少一个 on_unapplicable="block" 的 ColumnFilterRule。

第 5 步：执行 + 缓存 + 包装

SlayerSQLClient 按方言选择驱动：

数据库驱动异步性

缓存（可选，engine/cache.py）：

  • 键：sha256(final_sql + "|" + connection_string + "|" + runtime_fingerprint)
  • 失效：TTL 懒加载 + Cube 风格 refresh_keys（监控某张表某表达式的值）
  • 触发：只有 Python API 显式 cache=True 时生效；REST/MCP/CLI 默认不缓存

最后包装成 SlayerResponse：

class SlayerResponse(BaseModel): data: list[dict[str, Any]] # 行级结果 sql: str | None # 实际执行的 SQL attributes: ResponseAttributes # dimension/measure 元数据 (label, format) row_count: int query_runtime_ms: float query_warnings: list[str] = []

MCP / REST 层再把 SlayerResponse 序列化成 markdown / json / csv 字符串返回给客户端。

Cascade-on-Delete

当一个 model / datasource 被删除时，所有引用它的 memory 会被自动 strip——具体规则：

  • mydb.orders 同时 strip mydb.orders.amount（精确 + dotted 后代）
  • mydb.orders 不会 strip mydb.orders_archive（不是 dotted 后代）
  • memory:42 只 strip 精确匹配，不会 strip memory:421

9. 搜索与记忆

这是 SLayer 作为"Agent 优先"语义层区别于传统语义层的关键能力。

flowchart TB IN[search entities, query, question] --> S[SearchService] S --> C1[Channel 1: BM25
实体标签倒排] S --> C2[Channel 2: Tantivy
全文索引] S --> C3[Channel 3: Embedding
cosine 相似度] C1 --> RRF[RRF 融合 k=60] C2 --> RRF C3 --> RRF RRF --> OUT[扁平 SearchResponse
memories + entities + example_queries]

三通道

  • Channel 1 (BM25)：当提供 entities 或 query 时激活，对记忆的实体标签做 entity-overlap BM25。
  • Channel 2 (Tantivy)：当提供 question 时激活，在内存中建倒排索引，覆盖所有 memory + searchable entity。
  • Channel 3 (Embedding)：当 question + advanced_search extra 安装 + provider key 配置时激活，litellm 调嵌入 API 做余弦相似度。

三通道结果用 Reciprocal Rank Fusion (RRF, k=60) 融合成单个排序的 results 列表。

Memory 系统

MemoryService 提供 CRUD + cascade。 Agent 可以通过 MCP 工具 save_memory 保存学习笔记，下次通过 search 召回。

典型用法

save_memory( learning="orders.is_returned in {0,1,NULL}; treat NULL as not returned", linked_entities=["orders.is_returned"], ) save_memory( learning="Paid revenue by status", linked_entities={ "source_model": "orders", "measures": [{"formula": "amount:sum"}], "filters": ["status = 'paid'"], }, id="kb.paid-revenue", )

11. 自动建模（Auto-Ingestion）

SLayer 最大的便利之一：接 DB → 自动建模型。 engine/ingestion.py 提供：

flowchart LR A[ingest_datasource_models] --> B[1. SQLAlchemy Inspector 反射 schema] B --> C[2. 识别 PK / FK / 数据类型] C --> D[3. SQLite 列做亲和性类型探测] D --> E[4. 构建 FK 图] E --> F{图无环?} F -->|否| G[RollupGraphError] F -->|是| H[5. 生成 ModelJoin
(基于 FK)] H --> I[6. idempotent_merge
不覆盖已有字段] I --> J[7. save_model 落盘] J --> K[8. 触发嵌入 refresh]

关键特性：

幂等 (Idempotent)

重复 ingest 不会覆盖已有的列/连接定义，只追加新增的。 漂移（schema 改了）的部分会出现在 validate_models 的 to_delete 列表里，需要人工确认删除。

类型精化（Type Refinement）

SQLite 列的声明类型只是 affinity hint。SLayer 会对每列做 100k 行采样，用 typeof() / ROUND(col) <> col / Python coerce 决定实际是 INT 还是 DOUBLE。

12. 术语表

术语含义
Semantic Layer位于数据库与消费者之间的"业务模型层"，统一暴露度量、维度。
Measure度量，如 revenue:sum。对应一个聚合表达式。
Dimension维度，group-by 的依据。
Time Dimension时间维度，带 granularity（day/week/month/…）和 date_range。
Mode A (SQL)用 sqlglot 解析的 SQL 字符串引用，__ 跨模型。
Mode B (DSL)用 Python AST 解析的公式，. 跨模型、: 聚合后缀。
RLSRow-Level Security，行级安全。
SessionPolicy会话级 RLS 策略，透明注入到 SQL 的 FROM (SELECT * FROM t WHERE …)。
EnrichedQuery富化后的查询对象，所有引用都已解析为完整 SQL 表达式树。
DAG (source_queries)多阶段查询的依赖图。引擎用 Kahn 排序，最后一段是 root。
Cross-Model Measure跨模型度量（customers.revenue:sum），用 inner CTE + LEFT JOIN 拆解。
Refresh KeysCube 风格缓存失效键，监控某张物理表的某表达式值。
RRFReciprocal Rank Fusion，多通道检索结果的融合算法。
Schema Drift数据库 schema 跟持久化 model 不一致的情况。
